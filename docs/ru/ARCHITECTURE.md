# Архитектура

## Форма: сервис, API-first

Платформа — постоянно живущий сервис (не CLI-сессия): БД + API + воркеры агентов + веб-UI «стол CEO». Один и тот же сервис разворачивается тремя способами по мере роста:

1. **Локально** (docker compose, single tenant) — dogfood-этап;
2. **Open source ядро** — то же самое, self-hosted у других;
3. **SaaS** — multi-tenant. Чтобы не перекрывать этот путь: `company_id` во всех сущностях с первого дня, никакой записи состояния на локальный диск как источник правды, секреты активов — в отдельном хранилище per-company.

## Слои жёсткости (как добавляются фичи)

Правило: чем ближе к семантике процесса, тем жёстче.

| Слой | Что это | Как меняется |
|---|---|---|
| **Ядро** | Жизненный цикл решения, гейты согласования, лимиты полномочий, event log, бюджеты | Код. Редко, осознанно. Это «конституция» — гарантия, что агенты не перепишут себе полномочия |
| **Роли/отделы** | Мандат, модель, allowlist инструментов, каденция отчётов, лимиты | Конфигурация (манифест роли). Новый отдел = новый манифест, без кода |
| **Скилы** | SOP «как делается работа»: как ревьюим код, как считаем экономику, как пишем отчёт | Markdown-документы в библиотеке компании. Добавляются на лету. Мета-петля: агент замечает системную проблему → драфт SOP → proposal → CEO согласовал → скилл в библиотеке |
| **Интеграции** | Внешние системы (git-хостинги, CRM, банк, аналитика) | MCP-адаптеры + строчка в allowlist роли. Ядра не касаются |

## Доступ к моделям: OpenRouter

Все LLM-вызовы платформы идут через **OpenRouter** как единый шлюз:

- **Модель — поле конфигурации роли**, а не зашитый вендор: совету доступны разные модели у разных ролей (что напрямую усиливает принцип адверсариальной делиберации), смена модели = правка манифеста.
- **Один ключ, единый биллинг** — расход по моделям виден в одном месте и напрямую ложится в опексы компании (домен CFO) и в телеметрию event log (стоимость вызова пишется в событие).
- **Фолбэки и лимиты** OpenRouter используем как первую линию отказоустойчивости.

Каверза: раннер IT-исполнителей на Claude Agent SDK требует Anthropic Messages API; совместимость этого формата через OpenRouter (или необходимость прослойки типа LiteLLM / отдельного прямого канала для раннера) — проверить в спайке, см. открытые вопросы.

## Память компании: БД + API платформы

Состояние организации — в Postgres. Основные сущности: `Company`, `Role`, `Proposal` (+ позиции C-level и разногласия), `Initiative`/`Task`, `Report`, `Escalation`, `Skill`, `Asset`, `Event`.

**Агенты работают с памятью только через API платформы** (платформа выставляет агентам собственный MCP: `propose_decision`, `claim_task`, `submit_report`, `escalate`, ...). Не сырые файлы: каждый вызов проходит валидацию (обязательные поля отчёта, проверка уровня полномочий) и автоматически ложится в event log. API — это «трудовой кодекс» в исполняемом виде; здесь живёт детерминированность.

**Контекст совета — по запросу, не скопом.** У компании много данных, и не все релевантны каждому вопросу. Реализовано в два слоя: статичное доссье в конфиге компании попадает в промпт позиций как факт, и tool-use — агент позиции сам запрашивает нужное через function calling; каждый вызов пишется событием `context_consulted {roleId, tool, args, ok}` и попадает в provenance позиции («CFO прочитал финсводку августа и два прошлых решения»), число вызовов на позицию ограничено (`BOARD_MAX_TOOL_CALLS`), их стоимость входит в учёт прогона.

**Цикл ревизии.** «Вернуть с вопросами» — не тупик, а виток дискуссии: возврат с непустой заметкой автоматически созывает совет заново. Каждая роль получает возвращённый документ целиком (после подачи он — корпоративная запись), вопросы CEO и свою прошлую позицию; ревизионные позиции пишутся слепо к чужим *новым* позициям, синтез обязан открываться прямыми ответами на вопросы CEO и говорить, что изменилось, а что осознанно нет. Новый документ (`<id>-r2`, `-r3`, ...) ссылается на исходный через `revises` и ждёт подписи как обычный proposal. Самозацикливания нет: каждый виток запускает только CEO новым возвратом.

**Chief of Staff — процессная роль (`kind: "staff"`).** Роль, которая никогда не пишет позицию в совете, не занимает деловую сторону и не голосует; её мандат — внимание CEO и целостность процесса принятия решений. У неё две работы. **Триаж уточнений:** прежде чем вопрос дойдёт до совета, один дешёвый вызов (≈500 токенов, temperature 0.2) решает, может ли совет ответить на вопрос как он задан, или сперва нужно то, что знает только CEO — намерение, ограничения, аппетит к риску. Всё, что есть в доссье или что достанет context tool, — работа совета, и спрашивать это у CEO нельзя. Остановка пишет `clarification_requested {id, questionEventId, questionText, byRoleId, questions}` и обрывает прогон на месте — ни позиций, ни документа, потрачен один вызов — до тех пор, пока `POST /api/companies/:id/clarifications/:clarificationId/answer` не запишет `clarification_answered` и не перезапустит прогон, пронеся вопросы и ответы во все промпты как высшую инстанцию. Один виток, не больше трёх вопросов, а триаж, который упал или не уложился в таймаут, всегда *пропускает* вопрос дальше (сломанный привратник не должен стоить совещания). **Авторство синтеза:** документ-предложение пишет Chief of Staff, а не член совета, — это снимает смещение «автор судит собственную позицию»: та же машинерия синтеза, но голос, который собирает позиции и фиксирует разногласия, не добавляя своего мнения. Компания, в конфиге которой нет роли `staff`, пропускает и то и другое: вызова триажа нет, документ подписывает член совета — ровно как раньше.

**Три слоя документов** (по шкале жёсткости):
1. **Процессные объекты** — Proposal, Task, Report, Escalation, Skill: жёсткая схема, жизненный цикл, ядро.
2. **Библиотека компании** — markdown с типизированным фронтматтером (`id, type, title, summary, ownerRoleId, tags, status: current|superseded, updatedAt`), версионирование событиями (`document_created/updated/superseded`). Шесть типов: `profile` (факты о компании/продукте, приоритеты; владелец CEO/COO), `policy` (действующие правила и ценности; CEO), `finance` (бюджеты, P&L, прогнозы, юнит-экономика; CFO), `analysis` (исследования, разборы экспериментов; Growth/Analyst), `agreement` (внешние обязательства; CEO/CFO), `note` (всё остальное — предохранительный клапан). Метрики живут в телеметрии/интеграциях (в библиотеке — только их разборы как `analysis`); роадмап — в слое 1; ADR и спеки — в активах. Governance: `policy` и `profile` меняются только через процесс решений (proposal → подпись CEO); остальные типы роли пишут сами в рамках полномочий.
3. **Активы** — санкционированный хаос: внутри продуктовых репо и внешних систем структуру не навязываем.

**Тулы контекста:** библиотека — `library_list({type?, owner?, tag?})`, `library_read({id})`, `library_search({query, type?})` (Postgres FTS), `library_write` (с проверкой полномочий, policy/profile — через гейт решения); память процесса — `decisions_list/read`, `tasks_list`, `reports_list/read`, `escalations_list`, `budget_summary()`; активы — `assets_list()`, `asset_read({assetId, path})`, `asset_search({assetId, query})` (адаптеры по типу актива, первый — git).

**Event log — фундамент, не фича.** Каждое действие — событие (append-only). Из него: аудит, телеметрия компании (скорость решений, cycle time отделов, расход денег/токенов против бюджета), материал для периодических отчётов.

## Задачи

Источник правды — БД платформы (Task с владельцем-отделом, зависимостями, статусной моделью, ссылкой на породившее решение). Внешние трекеры подключаются позже как **проекции** через интерфейс `TaskBackend` (первый кандидат — GitHub Issues для IT-отделов: задачи рядом с кодом, PR, видимость для людей). Семантика процесса на чужую модель данных не завязывается.

## Активы

Реестр активов: тип (git-репо, облако, рекламный кабинет, документ-хранилище), владелец-отдел, способ доступа (MCP-сервер / CLI), креды. Продуктовых репозиториев может быть несколько; deliverables живут в активах, служебное состояние компании — никогда.

## Исполнение агентов

- **Оркестрация процесса** — детерминированный граф с durable-гейтами: на шаге «ждём CEO» состояние сохраняется, ничего не крутится и не жжёт токены, ожидание — часы или дни. Кандидаты: LangGraph (`interrupt()` + Postgres checkpointer) или Temporal; выбор — на этапе технического спайка.
- **Воркеры-исполнители** — stateless-запуски агентов по задаче: для IT-задач естественный раннер — Claude Agent SDK (headless) в песочнице с доступом к активу; для документных задач — прямые LLM-вызовы с инструментами платформы. Один stateful цикл на инициативу, исполнители одноразовые.
- **Пробуждение** — событийное: поступление задачи, завершение зависимости, cron отчётного цикла, эскалация.

## Аналитика — два разных контура

1. **Телеметрия компании** (встроенная): дашборд CEO поверх event log — прохождение решений, cycle time, бюджеты, буксующие отделы.
2. **Бизнес-аналитика домена** (работа отделов): аналитический отдел ходит в реальные источники (БД продукта, платёжки, веб-аналитика) через MCP-интеграции и производит отчёты-артефакты. Платформа даёт механизм подключения источников, а не готовые дашборды.

## UI «стол CEO»

Не чат, а рабочее место руководителя: inbox решений на согласование (с позициями и разногласиями совета), лента отчётов, эскалации, дашборд телеметрии, роадмап. Drill-down в любой уровень (вплоть до трейсов исполнителей) — по желанию, не по умолчанию. Чат с любой ролью — как дополнительный канал, не основной.

**Два режима, один набор экранов.** Веб-приложение показывает свои четыре экрана (Этаж, Стол, Отчёты, Метрики) поверх одного из двух провайдеров за общим хуком: **demo** — сценарный день из Phase 0 с полосой воспроизведения; **live** — реальная компания через API платформы. В live-режиме клиент забирает журнал событий и сворачивает его тем же `reduce()` из `@csuite/contract`, которым пользуется сервер, — «как выглядит компания» выводится ровно в одном месте; транспорт — опрос с курсором `after=<seq>`, и SSE заменит его без правки экранов. Переключатель режима в верхней панели (запоминается; `?mode=live` перебивает на один визит) оставляет два режима визуально различимыми, как того требует роадмап от моков рядом с реальным.

Единственное, что действительно различается между режимами, — часы: `EventBase.ts` — это сим-минуты в демо и epoch-миллисекунды на сервере, поэтому форматирование времени, окна анимации и оси графиков идут через `TimeScale` на поверхности провайдера, а не через демо-хелпер `clock()`.

## Открытые вопросы (следующие спайки)

- LangGraph vs Temporal для durable-оркестрации (критерии: ops-сложность self-hosted, история для аудита, HITL-эргономика).
- Раннер IT-исполнителей: Claude Agent SDK headless vs собственный цикл на API — стоимость, песочница, лимиты; и его совместимость с OpenRouter (Anthropic Messages API через шлюз, прослойка LiteLLM или прямой канал как исключение).
- Формат манифеста роли и скила (совместимость с Agent Skills / subagent-форматом Claude, чтобы не изобретать свой).
- Модель прав для MCP-адаптеров активов (как ограничивать «руки» отдела рамками его актива).
- Первая компания для dogfood: какой реальный проект с реальными деньгами передаём в управление.
