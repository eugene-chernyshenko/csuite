# Концепция: компания агентов с человеком-CEO

## Видение

Сервис, в котором пользователь — CEO настоящей (пусть и маленькой) компании, а вся организация под ним — AI-агенты: совет директоров (C-level), отделы, исполнители. CEO ставит стратегические задачи, совет прорабатывает и приносит решения на согласование, согласованное нарезается в роадмап и исполняется отделами, наверх поднимаются отчёты и эскалации.

Это не визуализация-«офис» поверх чатов (таких проектов много, и все они read-only театр), а **слой управления**: процесс, полномочия, решения, отчётность. Применимо не только к IT-продуктам — отделы работают с любыми активами: код, аналитика, финансы, маркетинг.

## Ключевой сдвиг относительно существующих инструментов

Claude Code и аналоги — это «один главный агент + одно окно ввода». Здесь модель другая:

- **Главный UX-объект — решение (proposal), а не сообщение в чате.** У решения есть автор, обоснование, альтернативы, цена, риски, зафиксированные разногласия совета и статус: draft → на согласовании → approved/rejected → в работе → отчёт.
- **Внимание CEO защищено полномочиями.** К CEO поднимаются только решения на согласование, отчёты и эскалации. Всё остальное совет и отделы решают в рамках своих лимитов (бюджет до X — сами, внешние действия — только через CEO). Провалиться на любой уровень можно, но по умолчанию кухня не льётся потоком.
- **Прозрачность через артефакты.** Состояние компании читается из журнала решений, роадмапа, отчётов и event log — без раскопок в истории диалогов.

## Роли

Роль — устойчивый контекст, а не одноразовый субагент. У каждой роли — мандат (домен ответственности), полномочия, инструменты, каденция отчётов. Общая цель у всех ролей одна: вести компанию к успеху — растить бизнес, расширять рынки, не терять деньги и доверие клиентов. Мандат — это чей взгляд, а не боевая стойка: роль не «атакует» и не поддакивает, она отвечает за своё.

- **CEO — человек.** Единственный человек в системе, вершина иерархии.
- **C-level (совет):** например CTO (техриски, архитектура), CFO (деньги проекта: бюджет, P&L, unit-экономика — токены лишь строка в опексах), COO (операционка, сроки). Состав конфигурируем.
- **Отделы и исполнители:** программисты, тестировщики, аналитики, маркетологи — по нуждам компании.

## Процесс принятия решений

Совет — не групповой чат. Проверено (AI Village, исследования sycophancy): плоский чат агентов распространяет ошибки социально и производит фейковый консенсус.

1. CEO ставит стратегическую задачу.
2. Каждый C-level пишет **независимую позицию, не видя чужих** — из своего домена (CFO судит деньги, CTO — технологию и риски), опираясь на данные компании: доссье, финансовые сводки, метрики, журнал решений, задачи. Совет должен уметь **запрашивать** нужные данные, а не получать всё скопом — контекст компании велик и не весь релевантен каждому вопросу.
3. Синтезирующий шаг сводит позиции в решение, **разногласия фиксируются и показываются CEO**, а не сглаживаются.
4. CEO согласовывает / отклоняет / возвращает с вопросами.
5. Approved-решение декомпозируется в роадмап, задачи распределяются по отделам.
6. Исполнение → отчёты по задачам + периодические отчёты отделов → дашборд CEO.

Полноценная делиберация — только на стратегических решениях. Операционка идёт дешёвым путём без «совещаний» (ритуальные дебаты дороги и перформативны — подтверждено исследованиями).

## Два пространства

- **Память компании** — состояние организации: решения, роадмап, задачи, отчёты, event log, конфиги ролей, библиотека скилов. Живёт в хранилище платформы (БД). Не смешивается с deliverables.
- **Активы компании** — то, над чем она работает: продуктовые git-репозитории (их может быть несколько), рекламные кабинеты, облака, документы. Реестр активов фиксирует, какой отдел чем владеет и через какие инструменты ходит. Git — тип актива и инструмент IT-отдела, а не фундамент системы.

## Принципы (выводы из ресерча, сен 2026)

1. **Детерминированный каркас, LLM в узлах.** Оргструктура, жизненный цикл решения, гейты, каденции — код/конфигурация, а не импровизация LLM-«менеджера». (MAST: большинство провалов мультиагентных систем — ошибки оргдизайна.)
2. **Документы как медиум коммуникации.** Агенты обмениваются структурированными артефактами, а не пересказами в чате — это лечит «испорченный телефон» (урок MetaGPT).
3. **Один stateful цикл на рабочий поток, исполнители stateless.** Иерархия — в данных (дерево задач, ответственность), а не в глубине вложенности агентов (урок Cognition).
4. **Стюардство вместо атаки и поддакивания.** Проверено golden-кейсами (сен 2026): мандаты «атакуй X» дают стену единогласных «против» (совет отверг даже дешёвые бэкапы), а инструкция «спорь» фабрикует театральные разногласия (совет условно согласился на рекламу казино). Работает общая цель + домен ответственности + явный протокол разногласий: несогласие фиксируется, когда оно заработано, а не назначено.
5. **Расчёт на регулярные фейлы.** Честная планка индустрии — 30–43% выполнения реалистичных офисных задач (TheAgentCompany, NeurIPS 2025). Отсюда обязательные гейты приёмки, возврат задач, эскалации.
6. **Событийная экономика.** Агенты просыпаются по событиям и расписанию, а не крутятся вечно.

## Траектория продукта

Сервис с первого дня (не локальная игрушка): сначала запускаем локально для себя (dogfood), возможно открываем ядро в open source, **SaaS остаётся в горизонте планирования** — архитектурные решения не должны красить нас в угол single-tenant/single-machine.
